# 0.2.1 — Wave 3 behaviour fixes (patch)

Status: **PREPARED, NOT YET PUBLISHED.** `@coreguard/agent-commerce` is
`0.2.1` in `package.json`, `server.json` and the lockfile; the npm publish and
the MCP Registry republish happen through the gated release workflow
(`.github/workflows/release.yml`, manual run with `confirm=RELEASE`), which
requires the owner's `NPM_TOKEN`. Nothing in this file claims the version is
live until that run succeeds.

This patch adds no tools, no transport and no network path. It changes four
behaviours that the Wave 3 test file (`test/integrations/agent-commerce-wave3.test.mjs`,
29 tests) proved wrong while it was being written; the tests were not relaxed —
`wave3.mjs` was fixed. All four are visible in a tool response, so a caller that
pinned `0.2.0` output shapes should read the compatibility notes.

## Fixed 1 — `coreguard_compile_policy`: selectors and currency are normalised

`allowSelectors` entries are lowercased and `currency` is uppercased when the
policy is compiled. A spec written `"0xA9059CBB"` and an intent written
`"0xa9059cbb"` are now the same SELECTOR rule, and `"usd"` / `"USD"` are the
same CURRENCY rule.

**Compatibility note:** `policyDigest` for a spec that carries mixed-case
selectors or a lowercase currency changes once, because the compiled policy
bytes change. Specs already written in canonical case produce the same digest
as before. Re-compile and re-approve any pinned policy digest from 0.2.0 that
used mixed case.

## Fixed 2 — `coreguard_scan_tool_descriptions`: offsets point at the character's start

An astral code point (for example U+1F600 or a Unicode-tag payload) occupies two
UTF-16 units. The scanner consumed the low surrogate and then reported that
consumed index, so every finding on such a character was reported one position
past where the character starts.

**Compatibility note:** `findings[].index` is now the exact start index — it
matches `description.slice(index, index + 2)` for an astral character. Findings
on astral characters shift by −1; BMP findings are unchanged.

## Fixed 3 — `coreguard_check_lookalike`: punycode labels are decoded (RFC 3492)

The confusable skeleton was computed over the raw label, so a homoglyph written
in punycode (`xn--…`) compared as an unrelated ASCII name — exactly the trick
the check exists to catch. Each label is now decoded with an in-module RFC 3492
decoder before folding.

**Compatibility note:** domains with `xn--` labels can now return
`lookalike: true` where 0.2.0 returned `false`. An undecodable label is kept
raw, the scan still reports the `punycode` signal, and no network resolver is
involved.

## Fixed 4 — `coreguard_freeze_agent`: honesty and idempotence of the freeze report

The control-plane ledger only moves an approval `pending → approved|rejected`;
an already-approved approval cannot be re-decided. 0.2.0 counted those as
"rejected", which reported a decision the ledger never recorded, and a second
freeze re-reported them.

Now:

- `pending` approvals are rejected in the operation (`approvals.rejected`,
  `rejectedApprovalIds`);
- already-`approved` approvals are reported as **superseded** by the agent
  revocation (`approvals.approvedSuperseded`, `approvedSupersededIds`) — the
  ledger denies them at `evaluate()` time, and the response says so in `note`;
- `approvals.open` still counts both groups, so the number is not silently
  deflated;
- a second `freeze_agent` on the same agent reports `approvedSuperseded: 0` and
  no re-rejection of approvals the first call already handled.

**Compatibility note:** the response gains `rejectedApprovalIds`,
`approvedSupersededIds` and `note`. A caller that read `openApprovalIds` to mean
"approvals that were rejected" must read `rejectedApprovalIds` instead.

## MCPRush studio, after the npm publish succeeds

The listing reads the published package; the repository cannot press these.

1. **Confirm npm first:** `npm view @coreguard/agent-commerce version` → `0.2.1`.
2. **Cut the release:** Studio → **Releases** → **Add new release** → **MCP server**
   → pick the listing → **Version** `0.2.1` → **What changed** (paste the four
   fixes above, one line each) → **Publish**. With *Settings → Publish a release
   as soon as it is cut* off, the release waits as *held*: click **Serve it
   again**.
3. **Re-read the tool surface:** Studio → **MCP Servers** → **Manage** → the
   **Tool surface** row (this is the read path for a stdio server buyers reach
   directly) → read the tools again. Expected: 46 tools, no added/removed/
   widened tool, so no approval waits in **Dashboard → Changes**.
4. **Confirm the listing:** the release row reads `stable 0.2.1`, the tool count
   reads 46, and the install line names `@coreguard/agent-commerce@0.2.1`.
5. **Rescan the grade (only if it should change):**
   Studio → **MCP Servers** → **Manage** → **Security** → **Request a rescan**.
   Limit: once a day per listing, five a day across listings. The grade becomes
   whatever the scan finds; it is a scan of a code snapshot, not a review, and a
   rescan is a measurement, not an appeal. **Contest this finding** there sends
   one finding to a person.
6. **Nothing else to click:** publish remains free, sign-in stays `none`,
   variables stay `none`, and no adoption figure is claimed anywhere.

Sources for the studio path names: MCPRush docs, "Cut a release" and
"Security and trust → Publishers" (`mcprush.com/docs`), read 2026-11-25.

## Boundaries

The four fixes are arbitration over caller-supplied JSON: a compiled policy, a
description string, a domain string and a local control-plane ledger. None of
them contacts a network, a chain, a merchant or a payment provider, and none of
them turns `VERIFIED` into a safety claim. The freeze report describes ledger
state; it does not prove an agent is harmless, and `PASS`/`PASS ≠ SAFE` travels
unchanged.
