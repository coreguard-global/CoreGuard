# مواصفات MVP وخطة الاختبار — سلامة السعر والدفع (Pilot Salla Shop)

**وثيقة مرافقة لـ:** `COREGUARD-SALLA-SHOP-TECHNICAL-PILOT-PROPOSAL-v1.0.ar.md`  
**النطاق:** المرحلة 1 (Sandbox أولًا). تحدد هذه الوثيقة الآثار/الكائنات المقترحة، حالات النتيجة وأسبابها، وشكل التحقق والاختبارات لقبول pilot ضيق وقابل للقياس.

---

## 1) الأهداف

1. إثبات قدرة CoreGuard على التحقق المستقل من الاتساق بين **عرض/موافقة معتمدة** و**دفع مُلاحظ من الخادم** و**سياق الطلب**.
2. إنتاج **نتائج مُسمّاة** (`VERIFIED`, `MISMATCH`, `EXPIRED`, `REPLAY_DETECTED`, `PENDING`, `UNKNOWN`) مع أسباب قابلة للقراءة آليًا.
3. إثبات التعامل مع إعادة الاستخدام/التكرار (replay/idempotency) ومتانة معالجة webhooks في بيئة sandbox.
4. تسليم حزمة أدلة/تقرير مناسبة للتقييم التقني.

**خارج النطاق (المرحلة 1):** استبدال أنظمة Salla للدفع/الحجز/النزاعات، تشغيل إنتاجي، استخدام أموال حقيقية، حكم آلي في النزاعات، أو ضمان منع كل الاحتيال.

---

## 2) الكائنات/الآثار المقترحة

### 2.1 عرض سعر قابل للتحقق (VPQ)
سجل مرتبط لما تم تسعيره وعرضه للموافقة.

**حقول مقترحة (حد أدنى):**
- `quote_id` (معرّف فريد)
- `order_id` / `cart_id` / مراجع البنود (حسب المتاح)
- `merchant_id` أو مرجع سياق الاستلام
- `fiat_amount` + `fiat_currency` (مثال: `100.00 EGP`)
- `pi_amount` + قواعد الدقة/التقريب
- بيانات `rate_source` (المزود، الزوج/الرمز، الطابع الزمني، المدخلات المستخدمة)
- `fx_context` (إن لزم مسار تحويل وسيط)
- مرجع المعادلة/إصدار الحساب `calculation_version`
- `created_at`, `expires_at`
- بيانات السلامة/الربط (`integrity`: بصمة/توقيع/ربط حسب البروفايل)

### 2.2 إيصال الموافقة (CGCR)
سجل مرتبط بموافقة العميل على عرض/نية طلب محددة.

**حقول مقترحة (حد أدنى):**
- `consent_id`
- `quote_id` (ربط)
- `approved_amount` (كما عُرض/اعتُمد)
- `approved_recipient` أو سياق التاجر/الاستلام
- `approved_at`
- سياق الفاعل (مرجع جلسة/هوية مستعارة حسب المسموح)
- `policy_profile` / النطاق
- بيانات `integrity`

### 2.3 مشاهدة الدفع (من الخادم)
مدخل مُطبّع من Backend لدى Salla (وليس من واجهة العميل).

**حقول مقترحة (حد أدنى):**
- `order_id`, `payment_id` / مرجع المعاملة
- `observed_amount`, الأصل/العملة، الشبكة/البيئة
- سياق الدافع/المستلم (حسب المتاح والمناسب)
- `status` ومؤشرات التأكيد/النهائية
- `event_id`, `event_type`, `event_time`, `idempotency_key`
- نتيجة التحقق من توقيع webhook (إن وجد)
- بيانات المصدر (استعلام API مقابل webhook، أوقات)

## 3) حالات النتيجة وأسبابها

### 3.1 الحالات الأساسية
| الحالة | المعنى | معالجة نموذجية (حسب السياسة) |
|---|---|---|
| `VERIFIED` | نجحت الفحوصات المطلوبة | متابعة/تسجيل أدلة |
| `MISMATCH` | تعارض في البيانات | إيقاف/مراجعة/منع حسب السياسة |
| `EXPIRED` | انتهت نافذة الصلاحية | طلب عرض/موافقة جديدة |
| `REPLAY_DETECTED` | إشارة إعادة استخدام/تسوية مكررة | منع الأثر المكرر وتنبيه/مراجعة |
| `PENDING` | انتظار تأكيد/أدلة مطلوبة | انتظار/إعادة محاولة |
| `UNKNOWN` | أدلة غير كافية أو غير موثوقة | إغلاق آمن للإجراءات الحرجة |

### 3.2 أسباب مقترحة (مجموعة أولية)
| الكود | الحالة | الوصف |
|---|---|---|
| `AMOUNT_UNDERPAID` | `MISMATCH` | المبلغ المرصود أقل من المعتمد (خارج السماحية) |
| `AMOUNT_OVERPAID` | `MISMATCH` | المبلغ المرصود أعلى من المعتمد (خارج السماحية) |
| `RECIPIENT_MISMATCH` | `MISMATCH` | اختلاف المستلم/سياق التحصيل |
| `ORDER_BINDING_MISMATCH` | `MISMATCH` | عدم اتساق ربط الطلب/الدفع |
| `ORDER_CONTEXT_MISMATCH` | `MISMATCH` | تغيّر شروط الطلب بعد الموافقة دون إعادة اعتماد |
| `CURRENCY_OR_NETWORK_MISMATCH` | `MISMATCH` | اختلاف الأصل/الشبكة/البيئة |
| `QUOTE_EXPIRED` | `EXPIRED` | انتهاء صلاحية العرض/الموافقة |
| `PAYMENT_REUSED` | `REPLAY_DETECTED` | إعادة استخدام نفس إثبات الدفع في سياق متعارض |
| `DUPLICATE_EVENT` | `REPLAY_DETECTED`/بدون أثر ثانٍ | معالجة مفتاح حدث مكرر مرة واحدة فقط |
| `CONFIRMATION_PENDING` | `PENDING` | لم يُستوفَ حد التأكيد المطلوب بعد |
| `EVIDENCE_INSUFFICIENT` | `UNKNOWN` | نقص حقول/تأكيد مصدر مطلوب |
| `WEBHOOK_INVALID` | `UNKNOWN`/مرفوض | توقيع/مخطط غير صالح أو حدث غير موثوق |

> تُحسم التسمية النهائية والتفاصيل مع دلالات نطاق Salla أثناء الاكتشاف.

## 4) شكل التكامل وواجهة التحقق (مقترح للـ pilot)

- **Adapter خاص بـ Salla** (جانب الخادم) يطبّع الكائنات/الأحداث إلى مدخلات تحقق CoreGuard.
- إعادة استخدام/توسعة قدرات Agent Commerce الحالية (`authorize`, `consent-verify`, `verify`, `risk-assess`) حيث يلائم، مع إضافة امتدادات pilot عند الحاجة.

**نقاط نهاية توضيحية (قابلة للتثبيت لاحقًا):**
| الطريقة | المسار (مثال) | الغرض |
|---|---|---|
| `POST` | `/v1/pilot/quote` | تسجيل/ربط VPQ |
| `POST` | `/v1/pilot/consent` | تسجيل/ربط CGCR |
| `POST` | `/v1/pilot/payment/verify` | التحقق من الدفع مقابل العرض/الموافقة/الطلب |
| `POST` | `/v1/pilot/webhook/verify` | تحقق ومعالجة idempotent لحدث webhook |
| `GET` | `/v1/pilot/report/:id` | استرجاع تقرير/ملخص الأدلة |
| `GET` | `/health` | فحص الجاهزية |

**حد أدنى لمحتوى تقرير التحقق:** `result_state`, `reason_codes[]`, المعرفات المُقيَّمة، نتائج الفحوصات، مراجع الأدلة، بيانات المُتحقق (CoreGuard/الإصدار/البروفايل)، والقيود/المجهولات.

## 5) خطة الاختبار (Sandbox)

### 5.1 المتطلبات المسبقة
- وصول sandbox واعتمادات محدودة النطاق (غير إنتاجية).
- إمكانية توليد/إعادة أحداث مُعقّمة: إنشاء عرض، موافقة، تحديثات حالة الدفع، webhooks (مكررة/غير صالحة).
- اتفاق على عتبة التأكيد وقواعد التقريب/السماحية.
- مخزن idempotency/replay معزول للتجارب.

### 5.2 السيناريوهات الأساسية (10)
| المعرّف | السيناريو | النتيجة المتوقعة | السبب/الفحص المتوقع |
|---|---|---|---|
| T-01 | مسار سليم | تطابق العرض/المبلغ/المستلم/الربط مع تأكيد كافٍ | `VERIFIED` | نجاح كل الفحوصات المطلوبة |
| T-02 | دفع أقل | مبلغ أقل من المعتمد | `MISMATCH` | `AMOUNT_UNDERPAID` |
| T-03 | دفع أعلى | مبلغ أعلى من المعتمد | `MISMATCH` | `AMOUNT_OVERPAID` |
| T-04 | استبدال المستلم | مستلم/سياق مختلف | `MISMATCH` | `RECIPIENT_MISMATCH` |
| T-05 | انتهاء العرض | إكمال بعد `expires_at` | `EXPIRED` | `QUOTE_EXPIRED` |
| T-06 | إعادة استخدام الدفع | نفس إثبات الدفع لطلب ثانٍ | `REPLAY_DETECTED` | `PAYMENT_REUSED` |
| T-07 | Webhook مكرر | نفس `event_id` مرتين | عدم تكرار الأثر | `DUPLICATE_EVENT` (idempotent) |
| T-08 | Webhook غير صالح | توقيع/مخطط خاطئ | رفض/`UNKNOWN` (حسب السياسة) | `WEBHOOK_INVALID` |
| T-09 | تأكيد معلّق | رُصد الدفع دون بلوغ العتبة | `PENDING` | `CONFIRMATION_PENDING` |
| T-10 | تغيير بعد الموافقة | تعديل الطلب دون موافقة جديدة | `MISMATCH` | `ORDER_CONTEXT_MISMATCH` |

### 5.3 سيناريوهات موسعة (موصى بها)
| المعرّف | السيناريو | النتيجة المتوقعة |
|---|---|---|
| T-11 | استرداد جزئي يتجاوز المتبقي | `MISMATCH` / مخالفة سياسة الاسترداد |
| T-12 | استرداد إلى مستلم/سياق غير متوقع | `MISMATCH` |
| T-13 | أحداث حالة متعارضة/خارج الترتيب | حسم حتمي حسب نموذج الحالة أو `UNKNOWN` مع فجوة أدلة |
| T-14 | نقص بيانات مصدر التسعير | `UNKNOWN` (`EVIDENCE_INSUFFICIENT`) لادعاءات سلامة العرض |

### 5.4 معايير قبول الـ pilot
- تنفيذ T-01–T-10 في sandbox مع توثيق المدخلات/المخرجات.
- كل نتيجة غير `VERIFIED` تتضمن سببًا قابلاً للفهم ومرجع أدلة على الأقل.
- عدم حدوث أثر مزدوج في T-07.
- تمييز واضح بين `PENDING`/`UNKNOWN` وبين `VERIFIED` و`MISMATCH`.
- تسجيل القيود والافتراضات غير المُتحقق منها صراحة.

## 6) المخرجات

1. مواصفة تكامل (خرائط الحقول، مصفوفة مصدر الحقيقة، مخططات الحالات).
2. Adapter/تهيئة pilot قابلة للتشغيل في sandbox.
3. حزمة أدلة الاختبارات (مدخلات مُعقّمة، مخرجات، تقارير).
4. تقرير تقييم pilot (نتائج، فجوات، توصيات أمان/تشغيل، وخطة المرحلة 2).
5. قالب تقرير تحقق يحمل إسناد CoreGuard (بالاتفاق).

---

## 7) قرارات مفتوحة (تُحسم في الاكتشاف)

- عتبة التأكيد/النهائية المعتمدة لاعتبار الدفع "متحققًا".
- قواعد التقريب/السماحية لتحويل fiat↔Pi.
- سياسة TTL/انتهاء العرض وإعادة الموافقة.
- المعرفات القياسية لمفاتيح idempotency عبر webhooks والاستعلامات.
- نموذج الاحتفاظ بالبيانات/الأدلة وإخفاء الهوية والوصول.
- نطاق التقوية الإنتاجية وحدود الملكية التشغيلية.
